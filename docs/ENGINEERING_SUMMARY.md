# Final Engineering Summary

## 1. Plan and rationale

**Problem.** Show that an agentic system can take a requirement (well-defined, a change to
existing code, or vague) to a reviewable engineering outcome *with controlled autonomy*: agents
do multi-step work, the system verifies it, and humans keep authority over the decisions that
matter.

**Approach.** I built the *orchestrator* and let it build the *product*. The URL shortener is
generated by agents under governance, never written by hand. That forces the orchestration
layer to be real: if the gates, rollback, re-planning or approvals were cosmetic, the scenarios
would fail.

**Build order (and why).**
1. *Domain + state + audit first* (graph, artifacts, hash-chained events). Every later feature
   (lineage, metrics, resume, re-planning) depends on durable, trustworthy state.
2. *Governance before agents* (policy, approvals, tool guard), so no agent ever ran ungoverned.
3. *Engine* (scheduler, gates, retries, rollback via git worktrees, safe-stop, re-planner).
4. *Agents* as thin role prompts + structured output schemas + **deterministic exit gates**.
5. *Offline end-to-end tests* with a scripted provider and injected faults, so every control
   path (retry, rollback, repair, clarification, amendment, stop/resume, budget) is proven
   before spending on live runs.
6. *Live scenarios* with Claude (Opus 5.5) via the Messages API.
7. *Oversight surfaces*: CLI and dashboard.

## 3. Risks, trade-offs and validation

| Risk | Mitigation / validation |
|---|---|
| Agents produce plausible but wrong code | Agents never self-certify: tests, coverage, API contract against real routes, FR traceability and policy scans are deterministic gates. Separation of duties (test author ≠ implementer); repairs that touch tests need human approval. |
| Parallel agents corrupt each other's work | Disjoint file ownership enforced at design time; every attempt in its own git worktree; serialised merges; conflicts become failed attempts with feedback. |
| Runaway cost or loops | Per-agent turn limit, per-node attempt limit, bounded repair cycles and clarification rounds, run cost budget, circuit breaker → safe stop. |
| Unsafe actions by agents | No shell; command allow-list; workspace-confined paths; forbidden paths; secrets stripped from env; dangerous-code rules block merges. |
| Stale approvals after change | Approvals bound to content hashes; superseded on re-plan; changed design needs fresh sign-off. |
| Tampered history | Hash-chained audit log with verification command. |
| Vendor lock-in / outages | Provider interface (Anthropic + OpenAI-compatible); transient errors retried with backoff; fatal provider errors safe-stop and resume later. |

Trade-offs are detailed in [TESTING.md §5](TESTING.md#5-trade-offs) and the decision table in
[ARCHITECTURE.md §5](ARCHITECTURE.md#5-key-decisions-and-why).

## 4. Assumptions

* A single host runs the orchestrator; SQLite (WAL) is adequate for prototype concurrency.
* Generated services target Python/FastAPI/SQLAlchemy. The conventions are in the prompts, and
  the stack is enforced by the dependency allow-list.
* Agent commands may use the orchestrator's interpreter (dependencies pre-installed).
* The operator running the CLI or dashboard is the accountable human (identity = `--operator`).
* Brownfield scenarios evolve the code produced by the latest successful greenfield run. Any
  local repo path works as a seed too.

## 5. Limitations (honest list)

* Process-level sandboxing only (no container/network isolation for agent commands).
* Single-host state; no multi-tenant RBAC on approvals (optional shared token only).
* Regex/AST policy scanning, not full SAST; no dependency CVE scan yet.
* Docs aren't regenerated after late repair loops.
* LLM output is non-deterministic: scenario runs differ in detail. Gates guarantee conformance,
  not optimality.
* Cost figures are estimates from list prices.
